# 麒麟系统适配方案

> 状态：gienx package 已通过麒麟真机基础运行与 sandbox 验收；Electron 壳待集成验收
> 日期：2026-08-14  
> 适用范围：把 `codex-rs` 打出的 `gienx` 二进制作为 Electron（如 gientech-agent）核心，跑在国产银河麒麟桌面机上。  
> 相关文档：`gienx/packaging/DESIGN.md`、`gienx/packaging/DOWNLOAD.md`、`gienx/BUILD-AND-TEST.md`

---

## 1. 结论（先看这个）

1. **目标机不是麒麟 V11。** 真机是 **银河麒麟桌面操作系统 V10 SP1（2503）**，`aarch64`，**glibc 2.31**，内核 **5.4.18**。
2. **不要降级 Rust 1.95、edition 2024、tokio / reqwest / rustls。** 官方 `aarch64-unknown-linux-gnu` 基线是 kernel 4.1+ / glibc 2.17+，1.95 能在这台上跑，也能用来编这台要用的二进制。
3. **要压的是 link 用的 glibc，不是 crate 版本。** 在 Ubuntu 22.04（glibc 2.35）或 24.04+ 上裸编，这台机会报 `GLIBC_2.32+ not found`。
4. **当前发行矩阵没有 Linux ARM64。** `dist-workspace.toml` 只有 mac arm/x64、Win x64、Linux x64 gnu。现成 x86_64 Linux 包在这台上不能跑。
5. **sandbox 的阻塞点是旧 bwrap，不是 userns。** 真机 userns 已开且 `unshare` 实测通过；系统 `/usr/bin/bwrap` 是 **0.4.0**，会被现有启动器因缺少 `--perms` 直接丢弃。cargo-dist 又不带 bundled bwrap，Linux sandbox 会不可用。

本期适配目标：产出一份能在该真机启动的 `gienx` linux-arm64 包，并带上可用的 `bwrap`（以及 sandbox 用到的 `rg`）。

## 3. 仓库现状（与本期相关）

### 3.1 工具链与依赖

- Rust 锁定 **1.95.0**（`codex-rs/rust-toolchain.toml`）。
- workspace `edition = "2024"`，rustc 下限是 **1.85**。降 1.95 会把整仓编挂，且没有运行时收益。
- TLS：**rustls + aws-lc-rs**，不链系统 OpenSSL。`openssl-sys vendored` 只给 musl target。
- sqlite：bundled。
- `aarch64-unknown-linux-gnu` 是 Rust Tier 1 with host tools：kernel 4.1+、glibc 2.17+。
- aws-lc-rs 对 `aarch64-unknown-linux-gnu` 是一等公民，构建只需 C/C++ 编译器（非 FIPS 路径不强制 cmake/bindgen/Go）。
- aarch64 默认 outline atomics，运行时探测 LSE。编发行包时保持 `generic`，禁止 `-C target-cpu=native`。

### 3.2 当前发行矩阵

`dist-workspace.toml`：

```text
aarch64-apple-darwin
x86_64-apple-darwin
x86_64-pc-windows-msvc
x86_64-unknown-linux-gnu
```

已确认过的约束（见 `gienx/packaging/DESIGN.md` §14）：

- `precise-builds = true`，只编 `codex-cli`（产物名 `gienx`）。
- 不可 `cargo build --workspace`：会拖进 `realtime-webrtc`（C++ FFI）和 `codex-bwrap`（编 bubblewrap 要 libcap）。
- `x86_64-unknown-linux-musl` 曾因 rust-std 未就绪去掉，**本期也不走 musl 主路径**。

### 3.3 Linux sandbox 运行时结构

`gienx` 用 arg0 自调用充当 `codex-linux-sandbox`，不必再发一个同名独立二进制。真正隔离是：

- 默认：**bubblewrap + seccomp**（`linux-sandbox`）
- 备用：legacy Landlock（本机内核 5.4 **不可用**）

bwrap 查找顺序（`codex-rs/linux-sandbox/src/launcher.rs`）：

1. PATH 上的系统 `bwrap`，且 `--help` 必须含 **`--perms`**（`--argv0` 可选，0.9.0 才有）
2. 安装上下文或可执行文件旁的 `codex-resources/bwrap`
3. 都没有 → panic：`bubblewrap is unavailable`

系统 0.4.0 没有 `--perms`（约 0.5+ 才有）也没有 `--argv0`，第 1 步会被跳过。当前 cargo-dist 单文件包没有第 2 步。

上游完整包形态见 `scripts/codex_package/README.md`：

```text
bin/<entrypoint>
codex-resources/bwrap          # Linux
codex-path/rg                  # sandbox 展开 glob 会调 rg
```

本期 Linux ARM 包应按这个结构靠拢，而不是只丢一个 `gienx`。

## 4. 要不要降级

| 对象 | 决策 | 理由 |
|---|---|---|
| Rust 1.95 / edition 2024 | **不降** | 编译期约束；官方 aarch64-gnu 只要 glibc 2.17；降到 1.84 及以下整仓编不过 |
| tokio / reqwest / rustls / aws-lc-rs | **不降** | 与麒麟用户态 ABI 无关 |
| 系统 OpenSSL | **不依赖** | 主路径 rustls |
| **构建机 glibc** | **必须压到 ≤ 2.31** | 这是唯一要「降」的东西 |
| musl 静态链接 | **本期不做主路径** | 已踩过 rust-std；sandbox/aws-lc 成本高 |
| Electron 壳 | **单独锁版本** | 与 rustc 解耦；新 Electron 常把 Linux 基线抬到 glibc 2.35 |

一句话：降的是「在哪套 sysroot 上 link」，不是「用哪版 rustc」。

### 4.1 构建环境对照

| 构建环境 | 产物 glibc | 本真机 |
|---|---|---|
| Ubuntu 24.04 / 26.04 / `ubuntu-latest` | 2.39+ | 必挂 |
| Ubuntu 22.04（误按 V11 时的建议） | 2.35 | **也会挂** |
| **Ubuntu 20.04 / Debian 11 容器** | **2.31** | **能跑** |
| manylinux_2_28 | 2.28 | 能跑，更保守 |
| **在本真机原生编** | 2.31 | 最不容易踩 ABI |

GitHub 已无 `ubuntu-20.04` runner。推荐：

- ARM runner（`ubuntu-22.04-arm` 或自建）里跑 **`ubuntu:20.04` / `debian:11` 容器** 再编；或
- 直接在目标长城机装 rustup 1.95 原生 `cargo build --release -p codex-cli`。

交叉编译可以，但必须用 **glibc 2.31 的 aarch64 sysroot**，不能链构建机本机 22.04/24.04 的 libc。

## 5. 运行时适配点

### 5.1 主二进制 `gienx`

- target：`aarch64-unknown-linux-gnu`
- 动态链接 glibc，最高符号 **≤ `GLIBC_2.31`**
- 保持 rustls + aws-lc-rs；证书走系统 CA（`rustls-native-certs`）。内网国密 SM2 中间人 **不支持**，要换证书或加普通 TLS 代理，不是降 crate 能修。
- CPU 按 generic aarch64。鲲鹏 / 飞腾都不该开 `native`。

### 5.2 bundled `bwrap`

必须随包提供，建议：

- 版本 ≥ **0.9**（同时有 `--perms` 和 `--argv0`）
- 同样 `aarch64` + glibc ≤ 2.31
- 放到 Electron / 安装布局的 `codex-resources/bwrap`（`InstallContext::bundled_resource("bwrap")`）
- 构建需要 **libcap**（全工作区编 `codex-bwrap` 时曾因缺 libcap 失败）。容器里装 `libcap-dev`。
- `gienx` 依赖图里仍会编到 `openssl-sys`（gnu 目标不走 vendored），Debian 11 镜像需装 `libssl-dev`。
- 源码在 `codex-rs/vendor/bubblewrap`，构建入口 `codex-rs/bwrap/`。

系统 0.4.0 **不要**当兼容依赖，也不建议在用户机上升级系统 bwrap（信创环境通常不能改系统包）。

### 5.3 `rg`

`linux-sandbox` 展开不可读 glob 时会 `Command::new("rg")`。发行包应带 linux-arm64、glibc 2.31 的 ripgrep，放到 `codex-path/rg`，并保证运行时 PATH 能找到。不要假设麒麟桌面预装了 `rg`。

### 5.4 sandbox 策略预期

| 机制 | 本真机 | 预期 |
|---|---|---|
| Landlock | 内核 5.4 | 不可用，不要当主路径 |
| seccomp | 一般可用 | 跟随 bwrap 流程 |
| user namespace | 已开，unshare 通过 | bwrap **可以**工作 |
| 系统 bwrap 0.4.0 | 会被启动器拒绝 | 必须 bundled |
| 无 bwrap 且走默认 sandbox | panic | Electron 侧需有降级策略（见 §6） |

若个别镜像关掉 userns（本台不是），不是降依赖能修：要么放开 `kernel.unprivileged_userns_clone`，要么产品开关走 `danger-full-access` / 关闭 sandbox。

## 6. Electron 外壳（gientech-agent）

`gienx` 是 sidecar，不绑 Node ABI，和 Electron 主版本解耦。但仍有三条独立约束：

1. 壳必须是 **linux-arm64**，与 sidecar 同 arch。
2. 新版 Electron/Chromium 经常要求 **glibc 2.35+**。本机只有 2.31，**不能跟 macOS/Windows 共用最新 Electron 线**，要单独锁仍支持 Ubuntu 20.04 arm64 / glibc 2.31 的版本。
3. 本机 userns 已开，Chromium sandbox 比预想乐观；仍需真机验证。不要先无脑加 `--no-sandbox`。`--no-sandbox` 只解壳，不解 `gienx` 的 bwrap。

`~/Documents/superclient` 已按 `binaries/<platform>-<arch>/` 保存打包输入。麒麟包应完整解压到：

```text
superclient/binaries/linux-arm64/
  bin/gienx
  codex-package.json
  codex-resources/bwrap
  codex-path/rg
```

Electron 另外需要的 `gienx-proxy`、`node`、`node_repl` 不属于本仓库生成的麒麟包，应由 superclient 的 Linux ARM64 打包流程另行提供。

最终 Electron 包应保持为：

```text
<process.resourcesPath>/
  binaries/linux/
    bin/gienx
    codex-package.json
    codex-resources/bwrap
    codex-path/rg
    gienx-proxy
    node
    node_repl
```

主进程应 spawn `process.resourcesPath/binaries/linux/bin/gienx`。`bin/` 的父目录存在 `codex-package.json` 后，`InstallContext` 才能按 package layout 找到 `codex-resources/` 与 `codex-path/`。不要只把 `gienx` 扁平复制到 `process.resourcesPath`。

## 7. 实施现状

**没有**把 `aarch64-unknown-linux-gnu` 加进 `dist-workspace.toml`。cargo-dist 默认在 Ubuntu 22.04+ 上编，产物 glibc ≥ 2.35，会被人误当成「官方 linux-arm64」拿到麒麟上跑挂。麒麟包走独立流水线，强制 Debian 11。

| 文件 | 作用 |
|---|---|
| `gienx/scripts/build-kylin-aarch64-package.sh` | 编 `gienx` + vendor `bwrap` + 同 sysroot 的 `rg`，strip 临时组包副本，组包并卡 glibc ≤ 2.31 |
| `gienx/scripts/check-glibc-max.py` | `objdump -T` 检查最高 `GLIBC_*` |
| `gienx/packaging/kylin-aarch64.Dockerfile` | Debian 11 + rustc 1.95 本地/CI 镜像 |
| `.github/workflows/release-kylin-aarch64.yml` | `ubuntu-22.04-arm` + `debian:11` 构建；打 tag 后挂到同一 GitHub Release |
| `gienx/scripts/download-codex-binaries.sh` | 额外解压到 `linux-aarch64-kylin-v10/` |

Release 资产名：`gienx-kylin-v10-aarch64-unknown-linux-gnu.tar.xz`（附 `.sha256`）。

本地构建（必须已在 aarch64 + glibc ≤ 2.31 环境，或进 Docker）：

```bash
./gienx/scripts/build-kylin-aarch64-package.sh
```

Apple Silicon 上（国内不要直拉 `docker.io`，会超时）：

```bash
cd /path/to/gienx
./gienx/scripts/docker-build-kylin-aarch64.sh
# 镜像挂了换：BASE_IMAGE=docker.1ms.run/library/debian:11 ./gienx/scripts/docker-build-kylin-aarch64.sh
```

无论原生还是 Docker 构建，宿主机产物都在仓库根目录：

```text
/path/to/gienx/dist/gienx-kylin-v10-aarch64-unknown-linux-gnu.tar.xz
/path/to/gienx/dist/gienx-kylin-v10-aarch64-unknown-linux-gnu.tar.xz.sha256
```

Docker 日志中的 `/src/dist` 就是宿主仓库的 `./dist`；`codex-rs/target/` 只是 Cargo 中间产物。手动给 Electron 项目准备输入：

```bash
mkdir -p ~/Documents/superclient/binaries/linux-arm64
tar -xJf /path/to/gienx/dist/gienx-kylin-v10-aarch64-unknown-linux-gnu.tar.xz \
  -C ~/Documents/superclient/binaries/linux-arm64
find ~/Documents/superclient/binaries/linux-arm64 -maxdepth 2 -type f -print
```

预期看到四个 package 文件；不要把 `.tar.xz` 原样放入 Electron，也不要只复制 `bin/gienx`。

打 `v*` tag 会同时跑 cargo-dist 与本 workflow。无 tag 时可在 Actions 里 `workflow_dispatch` 只出 artifact。

### 7.1 真机验收（必须在长城机上跑）

```bash
tar xf gienx-kylin-v10-aarch64-unknown-linux-gnu.tar.xz
ldd ./bin/gienx
objdump -T ./bin/gienx | grep -o 'GLIBC_[0-9.]*' | sort -u
./bin/gienx --version

ldd ./codex-resources/bwrap
objdump -T ./codex-resources/bwrap | grep -o 'GLIBC_[0-9.]*' | sort -u
./codex-resources/bwrap --help | grep -E 'perms|argv0'
```

通过标准：

- `gienx` / `bwrap` / `rg` 最高 glibc 符号 ≤ 2.31
- `gienx --version` 能打印
- bundled bwrap 的 help 含 `--perms`（最好同时有 `--argv0`）
- 开启默认 Linux sandbox 执行一条简单 shell 命令成功
- Electron 将完整布局投放到 `process.resourcesPath/binaries/linux/`，spawn `binaries/linux/bin/gienx`，arch 一致，无 `GLIBC_* not found`

### 7.2 失败时的产品开关

sandbox 起不来时，agent 应给出明确错误，而不是静默当成功。可选配置关闭 sandbox，供无法带 bwrap / 关了 userns 的镜像使用。

## 8. 非目标

- 不降 rustc、不改 edition、不换 rustls 为系统 OpenSSL。
- 不把 musl 当本期主交付。
- 不在本期做龙芯 `loongarch64`、V11、x86 麒麟（那些 ABI/内核不同）。
- 不改 sandbox 语义去迁就 0.4.0 系统 bwrap。
- 不把「在 Ubuntu 22.04 上编 Linux x64」的现有流程改坏；只新增 ARM + 2.31 基线。

## 9. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 构建机 glibc 过新 | 二进制在真机无法启动 | 20.04/Debian11 容器或本机编；objdump 卡点 |
| 只发单文件 `gienx` | sandbox panic | 随包 bwrap + rg |
| 系统 bwrap 0.4.0 被误用 | 已由代码拒绝，表现为「找不到 bwrap」 | 文档与包布局写清楚 |
| 个别批次关掉 userns | bwrap 失败 | 真机探测；产品开关 |
| Electron 过新 | 壳自己出现 `GLIBC_* not found` | 在真机检查 Electron ARM64 ELF 的最高 glibc 需求，再锁定兼容版本 |
| 飞腾缺 LSE/AES 扩展 | 极少数旧核 | generic + outline atomics；真机跑 TLS 握手验证 |
| 国密 TLS | rustls 连不上 | 代理或换证书 |

## 10. 决策记录

| # | 决策 | 选定 |
|---|---|---|
| D1 | 目标系统 | 银河麒麟桌面 **V10 SP1 2503**，不是 V11 |
| D2 | 目标 triple | `aarch64-unknown-linux-gnu` |
| D3 | rustc | 维持 **1.95.0** |
| D4 | 构建 glibc | **≤ 2.31**（Ubuntu 20.04 / Debian 11 / 本机） |
| D5 | musl | 本期不做主路径 |
| D6 | sandbox | bundled bwrap ≥ 0.9 + seccomp；不依赖系统 0.4.0；不用 Landlock |
| D7 | 发行形态 | Linux ARM 带 `gienx` + `codex-resources/bwrap` + `codex-path/rg` |
| D8 | Electron | 独立锁定 glibc 2.31 的 linux-arm64，不跟桌面最新线 |
| D9 | 发行通道 | **独立 workflow**，不加入 cargo-dist targets（避免 2.35 单文件被误用） |
